# Player reports

`player-reports` is owned by this API. Deploy migration `1782700000000-create-player-reports` through the existing cosmetics migration command before deploying the API. The game server's shared schema is read-only here. Existing clients are unaffected; new clients must handle an older API returning 404. This change does not deploy the API or create a public moderator frontend.

Authenticated players list `/api/v1/me/player-reports/matches?page=1&limit=20` and submit `POST /api/v1/me/player-reports/` with `gameId`, `reportedUserId`, `reason` and `details`. Reasons are `harassment`, `cheating`, `stalling`, `inappropriate_name`, and `other`; details trim to 10–2000 characters. The response is `{id,status,createdAt}`. The server derives the reporter from the JWT and requires a completed ranked match in the last 30 days with stored player/opponent account IDs. Migrated history without IDs and guest-only games are excluded. Match names are never used to infer identity; opponent display names come from the ID-addressed account directory.

Only five **new** reports per rolling 24 hours are accepted. A PostgreSQL transaction-scoped advisory lock keyed by reporter serializes quota counting and creation across API instances. The game UUID is validated and lowercased before storage; the UUID column and unique reporter/game/opponent key also prevent alternate-case duplicates. A repeated submission returns the original receipt even after its match ages out; it never replaces its allegation or counts against the quota again. A full quota produces the existing 409 conflict response. An ineligible match/opponent gives 404 without exposing another player's history.

The private report stores the original allegation separately from a server-read match snapshot: match/game IDs, date, format, score, team IDs and names, and account usernames at submission. Names and client allegations are untrusted plain text and must be escaped by any moderator UI. Game IDs correlate existing operator-held server logs; no arbitrary client log, file, URL or replay upload is accepted. Do not put access tokens/passwords in report details, telemetry, or moderator notes. No reporter identity or allegation is returned to the accused account. The cosmetics DataSource redacts report/review parameters and database error text from normal, slow and failed-query logs while retaining the SQL shape for diagnosis.

Administrators use `GET /api/v1/admin/player-reports/?page=1&limit=20&status=open`, `GET /api/v1/admin/player-reports/:id`, and `POST /api/v1/admin/player-reports/:id/reviews`. Review bodies contain `status`, a 3–2000 character `note`, and `expectedRevision`. Statuses are `open`, `investigating`, `resolved`, and `dismissed`. Row locking plus revision checking returns 409 for stale reviews; each successful review appends the authenticated administrator ID, prior/new status, note, timestamp and revision in the same transaction. Reopening a closed report is allowed and audited. There are no automatic bans, penalties, match annulments or outbound notifications.

Report and review rows retain immutable actor IDs without cascading account foreign keys, so account deletion cannot erase the moderation trail. Retention/removal is an operator policy and is not automated by this feature. The migration rollback drops evidence: do not run it against a live moderation archive without an explicit retention decision and backup.
