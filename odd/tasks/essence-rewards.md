# Feature: essence-rewards

Engram mirror: topic `odd/essence-rewards/tasks`, project `evolution`. Repository locator: `evolution-api/odd/tasks/essence-rewards.md`.
Objective: a reward system with a currency ("Esencia", code name `essence`) earned through daily and weekly missions and spent on existing cosmetics. Branch: `feat/essence-rewards` from `main`. Delivery strategy: `ask-on-risk`. Runner: `bun test`; lint `bun run lint`; type check `bun run build`.

## Context (facts verified in code on 2026-10-23)

- `evolution-api` never ingests match results. `EDOpro-server-ts` writes `matches`, `duels`, `points_ledger` and `user_achievements` directly into the shared Postgres on `GAME_OVER` (`EDOpro-server-ts/src/plugins/basic-stats`). The API only reads them and handles annulment.
- `matches` has one row per player: `id, user_id, game_id, best_of, player_names, opponent_names, date, ban_list_name, ban_list_hash, player_score, opponent_score, winner, season, points, player_ids, opponent_ids, anulled*, created_at, updated_at, deleted_at`. `duels` carries `turns`. There is no bot flag, duration or deck in these tables.
- Achievement progress is computed on read (`src/modules/achievements/application/GetUserAchievementRecord.ts`); unlocking happens in the game server.
- Season is `config.season` from the `SEASON` env var. No cron or scheduled-job mechanism exists in the API.
- Cosmetics (`src/modules/catalog/domain/Cosmetic.ts`) have no price. `EntitlementSource.PURCHASE` exists unused; grants go through `src/modules/entitlements/application/GrantCosmeticToUser.ts`. `CosmeticTier`: `STANDARD < REGISTERED < DONOR < EXCLUSIVE`.
- API-owned tables use the cosmetics DataSource (`src/cosmetics-data-source.ts`), migrations in `src/migrations/<timestamp>-kebab-case.ts`, tracked in `cosmetics_migrations`. Module layout `src/modules/<name>/{domain,application,infrastructure}`; routers in `src/server/routes/*-router.ts`, registered in `src/server/server.ts`.
- Infra available: Postgres 16, Redis 7 (API compose), Valkey 9 (game-server compose, used for ban lists and rate limit only).

## Decisions

- D1. Currency name: "Esencia" (English: Essence). Uncountable in UI copy ("300 de esencia"). Identifiers use `essence`.
- D2. Architecture: a worker process inside `evolution-api` (same codebase, separate entrypoint) reads `matches` by incremental cursor, runs a pure rules engine over match facts, and writes projections (mission progress, essence ledger). The game server is not modified. Webhook rejected (shared DB; loses events on API downtime; couples availability). Broker rejected (no volume justification; operational cost).
- D3. The rules engine is a pure function `(facts, state) -> events`, reused by the worker, the tests and any historical backfill.
- D4. Essence balance is never stored. `essence_ledger` holds signed deltas; balance is `SUM(delta)`.
- D5. Missions claimed with matches later annulled are not reverted. At claim time only non-annulled matches count.
- D6. Mission periods: daily = UTC calendar day (`YYYY-MM-DD`), weekly = ISO week UTC (`YYYY-Www`). No cron: periods are derived from `matches.date` and from the clock on read/claim.
- D7. Out of scope for this feature: battle pass, shop rotation, login streaks, desktop client UI, cosmetic dismantling, notifications.

## Specs

- S1. **Essence ledger.** Table `essence_ledger` (API-owned DataSource): `id uuid, user_id, delta integer not null (non-zero), kind ('mission' | 'daily_bonus' | 'achievement' | 'purchase' | 'adjustment'), reference_key text not null, created_at`. Unique index on `(user_id, kind, reference_key)` so every credit or debit is idempotent. Domain port `EssenceLedgerRepository` with `append(entry, manager?)` returning `"inserted" | "skipped"` (same shape as `PointsLedgerRepository.insertEntry`) and `balanceOf(userId)`.
  Acceptance: appending the same `(user_id, kind, reference_key)` twice yields one row; `balanceOf` is the sum of deltas; a purchase that would make the balance negative is rejected before writing.
- S2. **Mission catalog.** Table `mission_catalog`: `id uuid, code text unique, period ('daily' | 'weekly'), rule jsonb, reward jsonb, active boolean, sort_order integer`. `name` and `description` are jsonb `{ en: string, es?: string }` (English mandatory and fallback), resolved by the API from `Accept-Language` (`src/modules/rewards/domain/LocalizedText.ts`); `reward` is `{ type: 'essence', amount }` or `{ type: 'cosmetic', cosmeticId }`; this feature seeds only essence rewards, the cosmetic variant exists so future event missions need no migration or API contract change. `rule` is `{ metric, target, ranked?: boolean }` where `metric` is one of `duelsPlayed`, `duelsWon`, `rankedDuelsPlayed`, `rankedWinStreak`, `winUnder10Turns`, `winDifferentFormat`. Seeded by migration with the initial set:
  Daily pool (3 rotate per day, deterministic from the period key): `play_3` "Play 3 duels" (duelsPlayed 3, 20); `win_1` "Win 1 duel" (duelsWon 1, 20); `ranked_play_1` "Play 1 ranked duel" (rankedDuelsPlayed 1, 20); `win_other_format` "Win a duel in a format different from your previous duel" (winDifferentFormat 1, 20); `win_fast` "Win a duel in 10 turns or fewer" (winUnder10Turns 1, 20).
  Weekly (fixed): `weekly_win_10` "Win 10 duels" (duelsWon 10, 100); `weekly_play_20` "Play 20 duels" (duelsPlayed 20, 100); `weekly_ranked_streak_3` "Win 3 ranked duels in a row" (rankedWinStreak 3, 100).
  Daily bonus: completing all 3 daily missions of a day credits 30 with kind `daily_bonus` and reference `<period_key>`.
  Acceptance: the selection of the 3 daily missions for a given day is a pure function of the day key and the active pool; the same day always yields the same 3.
- S3. **Rules engine (pure).** `src/modules/rewards/domain/evaluateMatch(facts, state) -> { progress[], events[] }`. `facts` = one match as seen from one user: `gameId, userId, won, ranked, opponentRegistered, banListName, date, duels[{result, turns}]`. `opponentRegistered` is true when every opponent has a user id. Play metrics (`duelsPlayed`, `rankedDuelsPlayed`) count any match; win metrics (`duelsWon`, `winUnder10Turns`, `winDifferentFormat`) count only when `opponentRegistered` is true, so wins against anonymous guests never pay; `rankedWinStreak` is ranked by definition. `state` = that user's current progress per active mission in the match's period plus `lastFormat` and `rankedStreak`. No I/O, no clock, no randomness.
  Acceptance: unit tests per metric cover: play counts, win counts, ranked-only filter, streak reset on loss and on unranked duel (unranked does not break a ranked streak but does not extend it), `winUnder10Turns` true only when the user won the match and the deciding duels sum ≤ 10 turns per duel won (any duel won with ≤ 10 turns counts), `winDifferentFormat` compares `banListName` with the previous match of that user regardless of period, a match on 2026-10-25T23:59Z and one on 2026-10-26T00:01Z fall in different daily keys and the same weekly key when within the same ISO week.
- S4. **Worker.** Runs inside the API process (`src/index.ts`) when `REWARDS_WORKER_ENABLED=true`, holding a Postgres session advisory lock so only one instance processes; `src/worker.ts` is the standalone entrypoint for backfill. The worker reads from sources, each with its own cursor row in `rewards_cursor` (`source`, `last_created_at`, `last_id`): source `matches` (this task) and source `unranked_matches` (S9, T3c). Loop per source: fetch the next batch ordered by `(created_at, id)` after the cursor (for `matches`: `anulled = false` and `deleted_at is null`), join duels turns, compute facts per registered user (`matches`: one row per user; `unranked_matches`: one fact per non-null id in `player_ids`/`opponent_ids`, `won` from `winner_team`), call `evaluateMatch`, upsert `mission_progress` (`user_id, mission_id, period_key, value, completed_at`, unique on the three), persist `user_reward_state` (`user_id, last_format, ranked_streak`; a per-user `last_match_id` was dropped on 2026-10-24: the per-source cursor already fixes the position and nothing reads it), advance the cursor in the same transaction. Poll interval `REWARDS_WORKER_INTERVAL_MS` (default 3000). Processing waits `REWARDS_WORKER_LAG_MS` (default 5000) behind `now()` so a match whose duels rows are still being written is not read half-complete. Processing a match twice is a no-op because progress upserts are keyed and the cursor moves monotonically.
  Acceptance (rewritten 2026-10-24; the repo's tests and CI never open a database): use-case tests over in-memory ports prove one tick projects progress, state and cursor; a second tick with nothing new changes nothing; a batch split across ticks accumulates in source order; rows inside the lag window wait; a held lock skips the tick. Query-shape tests pin the SQL, and the SQL was executed by the independent verifier against a Postgres 16 scratch session (row comparison with null cursor, CASE WHEN boolean parameter, zipped unnest, advisory lock). Killing between batch and cursor commit cannot double-apply because both are one transaction. `matches.created_at`/`date` are `timestamp without time zone` in UTC: the source reads them through `AT TIME ZONE 'UTC'` and passes bounds as UTC wall-clock strings, so the cursor is host-zone independent.
- S5. **Missions API.** `GET /me/missions?period=daily|weekly` (auth: bearer of the user; amended 2026-10-24 from `/users/:userId/...` with owner-or-admin to the repository's `/me/*` convention used by loadout, cosmetics and emote bar, which needs no admin logic) returns, for the current period key, each mission with `code, name, description, target, value, reward, completed, claimed`; `name` and `description` are already localized from the request's `Accept-Language` (`es` or `en`, default `en`). `POST /me/missions/:code/claim` verifies `mission_progress.completed_at` for the current period key, inserts `mission_claims (user_id, mission_id, period_key, claimed_at)` (primary key on the three) and applies the reward in the same transaction: for `essence`, appends `essence_ledger` `{kind: 'mission', reference_key: '<mission_code>:<period_key>', delta: amount}`; for `cosmetic`, grants it through `GrantCosmeticToUser.runForUserId` with source `CAMPAIGN` before the claim row (idempotent grant, so a lost race keeps the entitlement and still reports the conflict); when it is the third daily claim of the day, also appends the `daily_bonus` entry (30, reference `<period_key>`). Responses: `200 { balance, reward }` where `reward` echoes the applied reward object; `409` with message `"Mission already claimed"`; `422` with message `"Mission not completed"` (new `UnprocessableError` mapped in `server.ts`); `404` for unknown code, inactive mission, or a daily mission outside today's draw. Only the current period can be claimed (previous days expire unclaimed).
  Acceptance: use-case tests over in-memory ports for each status, the daily bonus on the third claim, and the cosmetic path (entitlement granted, no ledger row); concurrent double submit is decided by the primary key (`INSERT ... ON CONFLICT DO NOTHING RETURNING`, pinned by a query-shape test); transport tests prove both routes reject a missing bearer; swagger drift test lists both operations as protected under tag `Rewards`.
- S6. **Essence and shop API.** `cosmetics.essence_price integer null` added by migration; `null` means not purchasable. Seeded defaults (amended 2026-10-24): DONOR 800; REGISTERED stays `null` because `EntitlementsGatekeeper.accessFor` already grants the REGISTERED tier to every signed-in user, so there is nothing to sell them; STANDARD null (free); EXCLUSIVE null (hand-granted) unless a price is set later. `GET /me/essence` returns `{ balance }`. `GET /shop` (bearer) lists active cosmetics with a non-null price as `{ id, type, tier, displayName, price, owned }`, where `owned` is decided by the gatekeeper (`canUse`: tier or per-user grant), the same gate that decides equipping. `POST /shop/:cosmeticId/purchase` (bearer): refuses with `409 "Cosmetic already owned"` when the gatekeeper already allows it; then in one transaction under a per-user advisory lock (`EssenceLedgerRepository.lockUser`): balance ≥ price else `402 "Insufficient essence"`, append ledger `{kind: 'purchase', reference_key: cosmeticId, delta: -price}` (a skipped append is also `409`, so a replay never debits twice), grant the cosmetic through `GrantCosmeticToUser.runForUserId` with source `PURCHASE` inside the callback so a failed grant rolls the debit back. Responses: `200 { balance }`; `402`; `409`; `404` not purchasable or unknown (new `PaymentRequiredError` mapped to 402 in `server.ts`). The shop never changes the catalog module: a rewards-side `ShopCatalogRepository` reads `cosmetics` by raw SQL.
  Acceptance: use-case tests for 200/402/409 (owned)/409 (replayed ledger)/404 and the lock-before-append ordering; query-shape tests for the shop repository and the ledger lock; transport tests prove the three routes reject a missing bearer and that 402 maps with its message; swagger drift test lists the three operations as protected.
- S7. **Achievement credit.** When the worker sees a new `user_achievements` row (second cursor over `user_achievements` by `unlocked_at, id`), it appends `{kind: 'achievement', reference_key: '<user_achievement_id>', delta: earned_points * 2}`.
  Acceptance: unit test for the delta rule; integration test for idempotency of the cursor.
- S9. **Unranked identity (cross-repo).** `unranked_matches` gains `player_ids` and `opponent_ids` as TypeORM simple-array `text` columns (comma-separated ids, nullable; amended 2026-10-24: this mirrors `matches.player_ids`/`opponent_ids` exactly instead of the `text[]` first written here, so the worker reads both tables with the same code). Guests have no id and are left out, so a guest-only side stores an empty list; rows written before the migration stay NULL. Migration in the `evolution-types` submodule (run by the game server); `UnrankedMatchSaver` in `EDOpro-server-ts` fills them from the `GAME_OVER` players' `id`, filtering nulls like `BasicStatsCalculator` does for ranked. Rollout: migration deployed before the server; historical rows stay unattributed. Then the worker adds source `unranked_matches` (S4). User rule (2026-10-23): "siempre que sea un usuario registrado"; wins require a registered opponent (S3).
  Acceptance: saver test proves registered ids are stored per team and guests omitted, and a guest-only match stores empty lists; server suite, tsc and biome clean.
- S8. **Docs and swagger.** Every new route declares tag `Rewards`, summary, `detail` and `security`; the existing swagger drift test passes. `docs/rewards.md` explains the currency, periods, the worker, the rules engine contract, how to add a mission, and how to run a backfill (`bun run src/worker.ts --backfill --from <date>`).
